# Pipeline leakage review (2026-10-30)

Reviewer: independent, read-only. Scope: the working tree at 2026-10-30 (branch `feat/final-product`, many uncommitted files; another agent was still editing exports and web files while this was read). Nothing was run against a database, a server, pytest or a paid service. Every finding below was verified by reading the code that produces it and the code that would guard it; the migration and policy claims were read from the SQL. Earlier reviews (`2026-10-29-review-security.md` F1 to F21, `review-pipeline.md`, `review-exports-web.md`) were taken as read: the findings they raised and that are now fixed in the tree are not repeated, and the ones still open are only referred to.

Leak classes: A cross-tenant, cross-account, cross-run, cross-owner. B client-output. C stage hand-off (lost, duplicated, stale). D secrets. E erasure.

## Summary by class

| Class | Result |
| --- | --- |
| A | Tenant isolation is sound for the new tables (RLS forced, owner policies, grants, insert-only, definer functions scoped to the context tenant). The incremental and resume carry checks account and tenant. Two real gaps are about the second owner of one tenant (private workspaces): a shared raw upload object is deleted under one user's view (F6), and a user-triggered export build does not see colleagues' accounts (F5). |
| B | The final scan covers every member of every delivered file (names, nested docx and xlsx parts, docProps, comments, workbook.xml, hyperlink relationships, releases, manifest). The gaps are about WHAT is checked, not where: tenant exclusions added after a run are not applied to files and web tables (F1), contact details are served from archived page copies (F4), a few client-bound strings carry client text (F9, F10). |
| C | The open question 13 ("repeating data") is answered: it is real, in the account-wide readers (F2). The Word and Excel files themselves are built per run and do not repeat. The change note compares against the wrong version on a rebuild (F7). |
| D | The log allow-list, URL-with-query refusal and exception scrub hold. Low-risk items only: client table values in one log line (F9), URL userinfo or query tokens kept verbatim in the archive (F10), the download token in a query string. |
| E | The largest gap. Tenant deletion erases 15 tables; about 140 other tables and every object store are in neither the erase, the blocked nor the never list, and no test forces a classification (F3). Person erasure stops at the people tables and the archive index (F8). There is no account deletion in the tree. |

## Findings

Severity: high = a promise made to the owner or the client is broken today; medium = broken under a realistic condition; low = defence in depth or hygiene.

### F1 (high, B/A) An exclusion added after a run is not applied to the files, the web tables, Download everything, Ask or the live sheets

Where:
* `src/exports/readers/pg.py:307-311` and `:558-563`: the build reads `tenant_settings_versions` for `account_runs.settings_version` (the version pinned when the run started) and applies THAT exclusion list.
* `src/views/materialize.py:79-110` builds the web tables once per run through the same reader and caches them (`view_materializations`); a later read returns the cached rows.
* `src/account_intelligence/replica/sheets.py:123,146` and `answers.py:404` use the pull-time flag `p.excluded`.
* The only readers of the CURRENT exclusions are `account_workspace._archive_policy` and `resolve_run` (which only refuses an excluded account domain).
* `src/exports/readers/exclusions.py` header states the opposite ("for a run read after the tenant excluded someone"), and `GUARANTEE(test_exclusions_hold_at_pull_and_render_time)` tests only a settings version that already holds the exclusion.

Failing scenario: an admin adds "Jane Doe" and a competitor domain to the exclusions on Tuesday. The research of Monday is rebuilt (`POST /v1/exports`, free) or simply downloaded: the People List still lists Jane Doe, the web People table (materialised Monday) still shows her, "Download everything" gives the stored files with her, and Ask answers from `people` rows that do not carry the new exclusion. The archive pages of the same account correctly hide her. A competitor domain added as an excluded company is not a forbidden term in the rebuilt files.

Fix (smallest safe): in `PgContentReader.read` take the UNION of the run's pinned exclusions and the tenant's current ones (`settings.current(s)`), and record an `exclusion_hash` in `view_materializations` so a changed exclusion list re-materialises; apply the same rule to the people and jobs `SELECT`s of `sheets.py`/`answers.py` (or read them through `text_excluded`). Stored files stay as delivered (they are versions); a rebuild is the remedy and should be forced when the exclusion hash differs from the one in the stored manifest. Also apply the filter to `content.sources`, `content.detections` and `urls_member` (`workspace_files.py:278`): today an excluded person's profile slug stays in `build/urls.json` and in the sources registry even if the person row is dropped, because `apply_exclusions` filters only `releases`, `people`, `findings`, `people_names` and `forbidden_terms`.

### F2 (high, C) Facts, people and postings repeat across the runs of one account in every account-wide reader (answer to open question 13)

Evidence:
* Facts are keyed per run: `write_key` hashes the run id (`grading/repo.py:38-43`, unique index `uq_facts_tenant_id_write_key`); `jobs_carry.py` deliberately re-records each carried fact for the new run, and a resume re-grades under a new run. Nothing supersedes an equal fact of an earlier run (`supersede` runs only inside one run; migration 0009 has no such trigger). `people` and `job_postings` are unique per `(run_id, key)` (`uq_people_run_person_key`, `uq_job_postings_tenant_id_run_id_posting_key`), and `jobs/repo.py` saves every posting of a run, carried ones included.
* Readers that select by `account_id` only, with no run filter:
  * `replica/workspace.py:261-275` (the five "key findings" of the account page: the same Confirmed fact appears once per run and fills the top five) and `:325-366` (the tab badges "People N", "Job postings N", "Tech", "News", "Sources N" on `web/app/(client)/accounts/[domain]/page.tsx:97-112`: `count(*)` over `people`, `job_postings`, `facts` of ALL runs).
  * `replica/sheets.py:101-135, 205-235, 290-312`: the live (pre-delivery) People, Jobs, Tech, News tables.
  * `replica/answers.py:320-340, 560-575`: Ask reads the newest 2,000 / 1,000 facts of the tenant, duplicates included, so a repeated fact crowds out others.
  * `api/routes/crm.py:80-100` `_items`: "the account's delivered output" is read with no run filter, oldest first, limit 10: it serves the OLDEST run's facts, and private ones are selected (only `payloads.Item` may filter).
  * `agents/production/people_links.py:105` `FactMentions`.
* The exported files are NOT affected (they read `run_id = :r`, `readers/pg.py:339-356`). So the account page badges disagree with the delivered files and with the web tables of the delivered run after any resume or incremental re-research (a 7,000 posting account shows 14,000 after the second research).

Failing scenario: research A finishes (1,200 postings, 40 people). The owner presses Resume on a stopped run or starts an incremental re-research: 1,200 carried plus 15 new postings are saved again under run B. The account page now says "Job postings 2,415" while the Jobs file says 1,215, and "key findings" shows each of the five facts twice. A fact that run B did NOT find again (a closed posting, a withdrawn claim) still shows as current from run A: stale data presented as current.

Fix: read through the account's CURRENT run set. Smallest: one SQL helper `current_run(account)` (the delivered run if there is one, else the newest finished) and add `AND f.run_id = :run` / `p.run_id` / `j.run_id` to the account-wide queries above (the file-shaped sheets already do this through `delivered_run`). For the facts of Ask, dedupe with `DISTINCT ON (f.fingerprint)` ordered by `created_at DESC` (the column exists and is `hash(account, attribute, normalised value)`). Alternatively, when a run finishes, set `superseded_at` on equal-fingerprint facts of earlier runs (the append-only trigger allows `superseded_at`/`superseded_by`/`status`); that fixes every reader at once but needs a migration-free but careful writer.

### F3 (high, E) Tenant deletion leaves most client data and every stored object

Evidence (`config/deletion.yaml`, `src/tenancy/lifecycle.py`, migrations 0020, 0091, `tests/system/test_erase_allow_list.py`):
* `erase` lists 15 tables. A comparison of `config/ownership.yaml` (owned and tenant lists) with `erase` + `blocked` + `never` shows 90 owned and 51 tenant tables in none of them. The ones that hold client content: `accounts`, `research_jobs` (goal, topic), `job_pipeline_runs` and `job_pipeline_passes` (the whole posting record, titles, locations, text references, claims, as JSON), `people_pipeline_runs`, `person_search_pages`, `person_events`, `person_post_pulls`, `coverage_rows`, `work_units`, `pull_manifests`, `prepulled_*`, `view_rows` and `view_materializations` (the web tables, cell by cell), `export_packages`, `internal_deliverables`, `run_documents`, `documents`, `document_passages`, `document_tables`, `document_table_rows`, `raw_files`, `research_files*`, `download_jobs`, `chat_threads`, `chat_turns`, `saved_views`, `signal_events`, `deltas`, `alerts`, `notifications`, `intake_drops`, `crm_*`, and, tenant-level, `model_reply_log.reply_text` (the model's extraction output) and `llm_calls`. Only `test_the_plan_and_the_database_erase_the_same_tenants` ties the YAML to the SQL list; nothing fails when a table is unclassified.
* `deliverables` ROWS are erased but the five files and the workspace zip stay in the bucket under `<tenant>/<account>/<run>/deliverables/<sha>` (`exports/store.py` header: "a sweeper ... is a listed follow-up"). `deletion.yaml` mentions only `raw_payload_objects`. `tenancy/storage.py tenant_prefixes()` ("offboarding deletes all of them") has no caller anywhere in `src/`; no code deletes the uploads, quarantine, raw files, branding, archive bodies, download parts or deliverables of a tenant. After the deletion the objects are also unfindable by row.
* There is no account deletion at all in the tree (`grep` of routes and web: only document and chat-thread deletes; `documents.py:464` says "the runtime may not delete accounts"). The owner's note that account delete asks for confirmation could not be matched to code in this working tree.

Failing scenario: a client leaves; an operator runs the approved deletion: `completed` is never reached (blocked), but even the part that runs removes `facts` and `job_postings` while the same postings (titles, descriptions' sentences, locations) stay readable in `job_pipeline_runs.record_json`, the web table rows stay in `view_rows`, and the finished Word and Excel files stay in storage.

Fix: (1) a test that every table of `ownership.yaml` is in exactly one of `erase`, `blocked`, `never`, `kept` (with a reason), failing on new tables; (2) add the derived tables above to `erase` (children first) and extend `erase_rows` in a new migration; (3) an object-delete adapter for `tenant_prefixes()` plus the deliverables prefix, called after the row passes; until it exists list `deliverable_objects` and `upload_objects` under `blocked` so the dry run says so; (4) decide and build account deletion (rows plus `tenants/<t>/accounts/<a>/` prefix) or state in the product that it does not exist.

### F4 (medium, B) Archived page and news copies, and `data/releases/*.md`, carry email addresses and phone numbers verbatim

Evidence: `docs/data-handling-people-data.md` states contact details are "raw payload only; removed from every derived field ... nobody in client output". `jobs/snapshot.py:98` honours it (`strip_pii`), the Jobs workbook honours it (`readers/jobs.py:275`), the people fields honour it. `archive_records.page_record` and `news_record` (`archive_records.py:151-196`) store up to 200,000 characters of page text with only `archive_guard` (tool names, provider names, denylist) applied; `archive.copy_from` redacts contact details only for `format = text` copies (`archive.py` `copy_from`); `release_text` (`workspace_files.py:465`) prints the text as stored. The archive page, its JSON download and the workspace zip's `data/releases/` therefore show every email and phone number a public page printed (press contacts, a recruiter's address on a careers page, "contact our CIO's assistant").

Fix: apply `archive_records.redact_contact` to the text fields in `page_record` and `news_record` at write time (and in `copy_from` for json copies already stored, and in `release_text`), as the posting snapshot does; add a test with an email and a phone in a page.

### F5 (medium, A/B) A user-triggered export build runs in user scope and does not see colleagues' accounts

Evidence: `api/routes/exports.py:82` calls `builder.build_all` inside the request; `PgContentReader.read` opens `tenant_txn(..., snapshot=True)`, which inherits the request's user scope. `_OTHER_ACCOUNTS` (`readers/pg.py:85,329`) and `RunInputAdapter.other_account_names` (`tracker/adapters.py:122`) then list only the caller's own accounts (owner policy on `accounts`). The worker path (`tasks.py:83 set_system()`) and the archive routes (`_archive_policy`: `tenant_txn(..., system=True)`) see all accounts, which is the stated rule ("other accounts' names, including colleagues' private workspaces, never appear").

Failing scenario: user B (a seller) rebuilds the files of her account; a page quoted in the Evidence file names the company a colleague researches in a private workspace. The worker build would have withheld or failed; the rebuild prints it, and stores the set as the account's new deliverable version.

Fix: build with `system=True` for the forbidden-term queries only (as `other_account_terms` does), or run `create_export`'s build through `with system_scope():` after the account is resolved under the caller's identity.

### F6 (medium, A/C) Deleting a document can destroy another user's raw file (same tenant, private workspaces)

Evidence: `raw_files` is one object per `(tenant, sha256)` (`raw_key(tenant, sha)`), the registry row is owned by the first uploader, and `documents` rows are owned by `uploaded_by`. Finalisation runs in system scope (it sees every owner's registry row, shares the object, `service.py:~512-530`). `DocumentService.delete` runs in the user's request: `documents_with_sha` (`repo.py:1225`) counts only the CALLER's documents (RLS), and `remove_raw_file` deletes only the caller's registry row. `service.py:1010-1020` then deletes the shared object when the caller has no other document with that hash.

Failing scenario: sellers A and B each upload the same product sheet. A deletes hers: count 0, the object `tenants/<t>/raw/<sha>` is deleted, B's document row still points at it and every later read of B's file fails (and B's "golden record" is gone). Reverse order gives the same.

Fix: count and delete under system scope for this one check (`tenant_txn(tenant, system=True)`) or add a `raw_file_in_use(tenant, sha)` SECURITY DEFINER function that counts across owners; keep the object while any document of the tenant has the hash.

### F7 (low-medium, C) `previous_manifest` ignores the run: the change note of a rebuild compares the run with itself

`exports/store.py:139-153`: the docstring says "the account's latest workspace BEFORE this run's sets", the SQL is `WHERE account_id = :a AND kind = 'workspace' ORDER BY version DESC LIMIT 1` and the `run_id` argument is never used. A rebuild with changed content of run R2 (a fixed bug, a new exclusion once F1 is fixed) gets R2's own earlier set as "previous"; the change line then describes the difference between two builds of R2 and the real R1 to R2 change note is lost. Fix: add `AND run_id <> :r` (and order by `built_at`), test: build R1, build R2 twice with different content, assert the note names R1.

### F8 (medium, E) Person erasure leaves the person in facts, evidence, searches and delivered files

`PgPeopleRepo.erase` (`people/repo.py:712-812`) nulls `people`, `person_sources`, `person_profiles`, `person_posts` and (since 0092) deletes the archive index rows. Not reached: `facts`/`fact_evidence` (the people pipeline records `people.<key>.title` with the profile URL as evidence and the title as the sentence, `people/claims.py`; reading facts that quote the person by name, `FactMentions`), `person_search_pages` and their payload bodies, `person_events`, `model_reply_log`, the delivered People and Evidence files and the workspace zip (objects), `view_rows` of the materialised People table, the stored archive bodies (the store has no delete). The function is not exposed through the API (D-06), which is why this is medium. Fix: when counsel's decision is made, extend the same transaction with a definer function that nulls `fact_evidence.url`/`supporting_sentence` and `facts.value_text` for facts whose evidence URL is in the erased set, deletes `view_rows` of the account, and queues a rebuild; document that delivered objects need the adapter of F3.

### F9 (low, D/B) `ask.route` logs client table values

`api/routes/ask.py:363-366` logs `matched_values` and `reason`. `matched_values` are values of low-cardinality columns of the CLIENT's uploaded tables found in the question (`replica/router.py:186-193`: company names, platforms, classes, possibly person names), and `reason` repeats them. `logs.yaml` says logs carry "ids, not text". The allow-list passes them because they are short strings without a URL or email. Fix: log the number of matched columns and values, or hash them.

### F10 (low, D/B) The archive keeps and serves the address exactly as stored

`archive._rows` stores `url.strip()[:2048]` (userinfo and query string kept; only `url_normalized` drops credentials). The same string is returned by `/archive/list` and `/archive`, printed on the `url:` line of `data/releases/*.md` (`release_text`) and compared in `policy.hides`. A source address with `user:pw@` or a signed query (`X-Amz-Signature`, `token=`) is therefore stored, shown and exported; the delivered files already refuse such addresses (`clean_http_url` in `exports/contenturls.py`). Fix: pass the stored address through `clean_http_url` (reject credentials) in `archive._rows`, and drop query parameters whose name matches a token/signature list when it is shown; the lookup key (`url_hash`) is unaffected.

### F11 (low, B) The pre-delivery gate's third-party-host check reads only part of each file

`documents/gate.py client_text` reads `word/*.xml`, `xl/worksheets/*.xml`, `xl/sharedStrings*`, `docProps/core.xml|app.xml` and `.md/.txt/.csv`; the host check (`third_party_domains`) and `rows_lost` use that text, so hyperlink targets (`*.rels`), comments, `workbook.xml` (defined names, sheet names), `docProps/custom.xml` and `.json` members are not looked at by the gate. For files the builder made and the stored hash still equals, the builder's `third_party_scan` already covers all of them (`verify._members`: every `.xml/.rels/.json/.md/.txt` and nested docx/xlsx), and the gate defers to it, so this is open only for a library account file or a file whose hash no longer matches. For those, `scan_package(data, ())` runs but `third_party_domains` does not. Fix: call `exports.verify.third_party_scan(data, kind)` in the gate for every file that is not `_builder_verified`.

### F12 (info, hygiene) Tracked fixtures name real accounts

`tests/exports/test_evidence_register.py:54-60` uses the reference account's legal name (the project note says no code, config or test names it); a real account workspace zip fixture (under `tests/fixtures/`, since parked in `unwanted-things/real-account-fixtures/`) is a real account workspace committed to git (including `data/sumble/*.json` raw tool results and `build/*.py`). Not a runtime leak. Replace the first with a synthetic name; decide whether the second may stay in the repository.

## Verified fine (checked and found guarded)

* RLS and grants of the tables added by 0086 to 0092: `link_archive` and `tech_stack_items` are forced-RLS, owner-and-tenant policies with check, insert-only (plus the single `archived_at` UPDATE column with a trigger that refuses any other change and any move backwards); both are in `ownership.yaml created_owned`, in `tests/isolation/matrix/matrix.yaml`, in `deletion.yaml erase` and in the `erase_rows` allow-list (0091); `erase_archive_urls` (0092) takes no tenant, only deletes the context tenant's rows of one account that holds an erased person, is owned by the NOBYPASSRLS `tenant_eraser`, search path fixed. 0087 to 0089 only alter tables that already have RLS. The owner column of both new tables is now filled from the account (F14 of the earlier review is fixed in `pipelines.py:640-659` and `archive._INSERT`).
* Continuation and incremental carry: `previous_delivered_run` joins `account_runs` on the same tenant and `r.account_id = :a`; `PgPostingRepo.load_previous` checks `r.account_id = :account` (a foreign run id resolves to nothing); `carry_job_facts` selects `run_id = :previous AND account_id = :a`; the run input keys are written only by the server (`lifecycle._incremental_keys`, `replica/jobs.py`), and `postings_previous_run` supplied in a body is not accepted by the research routes. `resume_from` is validated to the same account (`runs._resumable`) and the user's owner policy; `connectors/cache.py` and `llm/reply_cache.py` select inside `tenant_txn` (RLS) with the tenant in the Redis key; the reply key hashes the whole request, which embeds the account id in every payload reference, so an identical key cannot cross accounts. Reuse across USERS of one tenant is a design decision (see open questions).
* Cloud Task names: `run-<run>-slice-<n>`, `job-<job>`, `download-<job>`, `run-<run>-approval-timeout` (UUIDs, no tenant text, no account name); the document task carries a nonce.
* Module-level state: the `lru_cache`s are configuration or pure-text functions (`_scrubbed_memo` caches by text only, no run-specific terms); `StorePayloads._consent` is per run; `InMemoryCacheIndex` is test or single-process only; `identity.rate_limit` memory dicts are keyed by hash.
* Reads outside `tenant_txn`: every `untenanted_session` use is an identity lookup or an operator console count; the one data user (`documents.deliverables.backfill_imports`) reads only the tenant list then works per tenant in `tenant_txn`.
* Payload and object keys: `payload_key`, `archive_key`, `raw_key`, `part_key`, deliverable keys all start with the tenant id; `require_owned` / `tenant_of_key` refuse a key outside the session's tenant (including `..` and `//`); the archive routes call `require_owned` before reading a body; `StorePayloads.view` checks the tenant prefix.
* Final scan: `verify.scan_package` reads every member NAME and every `.xml/.rels/.json/.md/.txt` member of the file and of nested docx or xlsx files (docProps, comments, workbook.xml with defined names and sheet names, hyperlink relationships, sharedStrings, hidden sheets), `third_party_scan` the same members; the workspace zip is scanned whole (`releases`, `RESTORE.md`, `MANIFEST.json`, `build/*.json`, `notes/*.md`) with the files already scanned skipped by hash; a release copy that a rule refuses is left out and listed by an address hash; the build runs off the event loop (`asyncio.to_thread`). Hashes are exempt only in `.json` members.
* Build failure text: `BuildFailed` carries pattern strings (which can be a literal other-account name), but the run records only `failed.reason` and the rule codes; logs carry the message hash; `routes/exports.py` returns `packages.blocked(..., "build_failed")` with no text.
* Client text on the web: archive and sheet routes scrub through `scrub_client_text`, add the other-accounts and excluded-company terms (`_forbidden_terms`, `_archive_policy`), hide excluded persons by name and URL, drop provider-domain hrefs (also on the cell route), withhold a field not the whole copy; profile copies are never listed or served (`CLIENT_KINDS`); React escapes all cell text, `safeLink` refuses credentials, non-http(s), backslashes and over-long addresses; no `dangerouslySetInnerHTML` in `web/`.
* Logs and errors: `obs/logging.py` keeps only allow-listed keys, refuses values with a URL carrying a query, userinfo, email, token shape or control characters, replaces exception messages by class, code, hash and own-code location; the API handlers return typed problem bodies and never echo submitted values; the connector client keeps only five response headers and never logs request headers; provider keys are `SecretStr`.
* Proxy (`web/app/v1/[[...path]]/route.ts`): forwards an allow-list of headers and only the tenant cookies, same-origin check on writes, body caps, path-only error logging, `redirect: "manual"`.
* Object download: the Download-everything part needs the session, the job's owner, an unexpired token stored as a hash and `compare_digest`; the token is renewed on every status read.
* Carry semantics: carried postings are bucketed again for the new `as_of`, their status is refreshed only by evidence, an incomplete active-set pull leaves the stored status, nothing is deleted; the Jobs file registers a source for every listed posting.

## Open questions (owner or counsel)

1. F1: should the stored files of a delivered run change when an exclusion is added (rebuild forced), or only the web and the next version? The code and the `exclusions.py` header disagree today.
2. F2: which run is "the account's current output" for the account page, Ask and the live sheets: the delivered run, or the newest finished one? (They differ while a re-research runs.) Superseding equal facts of earlier runs would make every reader right at once; it changes what "history" means for the Library and the alerts, so it is the owner's call.
3. F3: is a tenant deletion meant to take the uploads, the archive bodies and the five files from storage? `deletion.yaml` calls itself a proposal and blocks `raw_payload_objects` for "crypto-shredding the tenant key"; with a per-tenant key that would also cover the deliverables, but nothing implements it. Which tables are "kept on purpose" (ledgers) must be written down.
4. F8 / D-06: person erasure (counsel): is nulling the people rows and the archive index enough, or must facts, view rows and delivered files be rebuilt?
5. Sharing inside a tenant: `tool_calls`, `model_reply_log` and the Redis cache index are tenant-level on purpose (never pay twice), so user B's research can adopt a pull that user A's private workspace paid for. No content crosses (the key is the full request), but cost and timing reveal that A researched the same company. Confirm this is accepted for private workspaces.
6. Carried facts: `jobs_carry` re-records the previous fact with `read_in_primary_this_run = true` although the posting page was not read in this run (the status is refreshed by the active feed only). The Summary may print "Confirmed" for a posting last read in an earlier research. Intended by the incremental design, but the Word wording does not say "as of the previous research".
7. No data-vendor-neutral scan exists for model vendor or model names (`client_output_denylist.txt` has no Claude, Anthropic, Kimi, Moonshot, Opus; `name_digests.yaml` holds one digest). The delivered files never print a model name today, and Ask names the model on purpose, so nothing leaks now; if the policy is that a client file must never name a model vendor, add them to the denylist.
8. `x-forwarded-for` is forwarded from the browser by the proxy and keys the sign-in throttle; confirm the edge overwrites it before the proxy.
