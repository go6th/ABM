Part 1 The big picture

What this website is, who it is for, how it was built, and what it is made of.

1 What this project is, in plain words

A sales-research website. A salesperson types a company name; the system reads the internet and the salesperson's own files, checks every fact, and hands back finished Word and Excel files.

The product is called Account Intelligence. The folder on disk is called ABM Generator; the company behind it is called 6th. ABM means *account-based marketing*: selling to a chosen list of companies instead of to everybody. For each company on the list a seller needs to know who the key people are, what technology the company uses, what jobs it is hiring for, what is in the news, and what to say in a first call. Doing that by hand takes hours. This system does it in the background.

What a customer sees

  1. They sign in (company single sign-on or a password) to a workspace that belongs only to their company.
  2. On the home screen, Ask, they can question everything the system knows. Answers cite numbered sources.
  3. They click Add account, type a company (or upload their own files such as spreadsheets and call notes) and see an estimate of what the research will cost. They press Start.
  4. A Research board shows the work running live. It can take hours, because it reads hundreds of pages.
  5. When it finishes they get an Account Summary (Word), a Sources and Evidence document (Word), three Excel workbooks (People, Job Postings, Tech Stack and Teams) and a zip with everything. The same tables are also shown on screen.
  6. They can schedule a refresh (every 3 days, weekly, every 2 weeks, monthly) and ask more questions at any time.

What makes it different from a chatbot

Most AI tools simply write what sounds right. This one is built around not trusting the AI. The AI is only allowed to *propose* a fact together with a sentence copied word for word from a web page. Plain code then checks that the sentence really is on that page, works out how reliable the source is, and decides the fact's grade (Confirmed, Probable, Hypothesis, Lead). The AI cannot write a grade, because the data format it must answer in has no field for one. Only Confirmed facts may be stated to a prospect as fact.

2 The one-page verdict

Read this page first. Everything else in the PDF backs these statements up.

What is good
  • The design is unusually careful for a vibe-coded project: separate customers are isolated by the database itself (row-level security), not only by application code, and there is a nightly self-test of that.
  • Every route on the server must be listed in a catalogue or it answers 403 (default deny). 219 routes match the catalogue exactly.
  • Money is handled with care: every paid outside call is written to an insert-only ledger before it is made and replayed afterwards, so a crash does not make you pay twice.
  • A lot of automated checking exists: about 4,260 tests, import-layer rules, route-catalogue checks, migration lints and generated-file drift checks.
  • The AI is boxed in: strict output formats, quotes verified word for word, grades computed by code, judges that can only lower a grade.
What is risky
  • All spending caps are switched off on staging (RESEARCH_CAPS=off), and so are the token guard and the dollar cap. The only hard brakes left are "three empty slices in a row" and per-call time limits. The owner's own notes say ~$500 was lost to failed runs earlier.
  • Documentation disagrees with the code in at least a dozen places (section 23). The guide in docs/guide was written on 29 October; the code has changed since.
  • Large parts are dead or only half-wired: the whole monitoring/alerts product, an alternative model router, four "security/metrics/registers/unitcost" packages that do nothing (one of them always says "all clear"), 18 redirect-only web pages, 73 API routes that nothing calls.
  • A real company's workspace file is committed in git history (GSK_workspace.zip under unwanted-things/). If the GitHub repository is not strictly private, that is a data leak.
  • Releases are manual (Cloud Build and gcloud). The automatic deploy workflows exist but may never have run. Nothing in the repo applies Terraform automatically.
  • The worker process has been killed repeatedly by slow or blocked code, and the single-core database has saturated once under load.
What to do first
  1. Confirm the GitHub repository is private; plan a history rewrite to remove the real-account zip.
  2. Decide whether the spending caps should stay off. If staging is used by anyone other than you, turn RESEARCH_CAPS back on.
  3. Never start a research run or run the eval/live tests without understanding they spend real money (section 26).
  4. Pick one source of truth for documentation and refresh it (this PDF can be that starting point).
  5. Archive or delete the dead code listed in section 24 so the next reader is not misled.

6 The life of one research

A research takes hours but web requests must be short. The design answer is to cut a run into slices, save progress after every step, and let a sweeper rescue anything that dies.

Step by step

#What happensWhere in the code
1The person types a company or uploads a file and sees an estimate of tokens and dollars (GET /v1/research/estimate).web /research/new
2POST /v1/research: in one database transaction it checks the monthly allowance, checks the estimate did not change (else HTTP 409 "estimate changed"), adds the account and reserves credits. A job row is created with status queued.api/routes/research.py, replica/credits.py, replica/jobs.py
3The job is committed first, then a Cloud Task for /tasks/research-job is queued. If the queue is unreachable the caller still succeeds and the sweeper retries later.replica/jobs.py
4The worker's run_job creates a run (scope, topic, models, token estimate), seeds the 33-row coverage checklist, and queues slice 0 as a named task run-<id>-slice-0. A duplicate name counts as success, so queueing is safe to repeat.runs/lifecycle.py create_run
5execute_slice takes the run lease (one worker per run; renewed every 20 s; another worker may take it after 90 s of silence), counts the slice, then runs the research graph under a 1,650 s timer, resuming from the checkpoint.workflow/runner.py
6If the timer fires and progress was made, the next slice is queued. Three empty slices in a row end the run as PARTIAL (no_progress), keeping everything found.workflow/runner.py
7When the graph finishes: build files, quality gate, deliver. The runner then ends the run through one function, lifecycle.finish, which settles credits once (never more than the real spend, never more than reserved) and notifies the owner.runs/lifecycle.py

Why a killed worker does not lose the run

  • Paid calls are written to the ledger before they are made. The next slice replays finished calls for free. Model replies are replayed the same way.
  • Lease with a heartbeat. If a worker is killed, Cloud Tasks redelivers the slice at about +10, +30, +70 and +150 seconds (eight attempts in total). The +150 s attempt is past the 90 s silence limit, so it takes the lease and resumes.
  • Named Cloud Tasks. Every hand-off has a stable name, so repeating it does nothing harmful.
  • The 5-minute sweeper (Cloud Scheduler calls POST /tasks/sweep) does six independent jobs: re-queue stuck documents, end orphaned runs (lease expired for 600 s), mark stalled runs, auto-resume stalled or lost company research (up to 5 times per chain), settle jobs whose run has ended, and restart anything committed but never handed to the worker.
A limit you should know

Checkpoints are saved per graph node, not per web page. A node such as pull or interpret that is killed re-runs whole; what saves the money is that its calls are replayed by exact key. Any change to a prompt, a search query template, config/skill/pull_plan.yaml or the URL-canonicalising rules changes those keys and can make a resumed run pay again.

9 How a fact gets its grade

The model proposes, the code decides. This is the single most important design rule of the whole product.

The checks, in order

  1. The cited page must be one this run stored, and the quote must appear verbatim in it (after normalising spaces and case).
  2. The value must be inside that quote. Hostile text (a page trying to instruct the model, or the planted canary string CANARY-7f3a9e) drops the claim.
  3. The source gets a tier (T1 first-hand company page, down to T4 unknown) and a freshness weight; sources from the same origin count once. That gives an engine score A to D.
  4. The product grade is the first rule that fires, in the order in config/grading_policy.yaml: no evidence, conflicting, internal only, primary read (Confirmed), unread match (Lead), aggregator only (Lead), engine A or B (Probable), engine C or synthesis (Hypothesis), engine D (Hypothesis).
  5. A second model, the judge, checks the claim against the quote. It can only lower a grade or drop the claim. If no judge is available the claim is capped at Probable and flagged unjudged.

Six layers that keep the AI from grading

  • No place to write one. Every model answer format forbids extra fields (extra=forbid), so a grade in a reply fails validation and the whole reply is rejected.
  • Grade is pure code (grading/engine.py, grading/product.py): no model, no I/O.
  • "Confirmed" needs a primary read recorded in the fetch ledger (how the text was really obtained), not anything the model said. Only a full-page scrape counts; a search snippet or cached copy does not.
  • Evidence is verified by code: fabricated quotes, links, titles, names or tenures are dropped and counted.
  • Guard G2 stops the run if code ever gives an unread keyword match any grade above Lead (this once ended a run on 28 Oct; fixed).
  • Single write path: facts are written only by grading/repo.py, append-only.
Where the rule has holes

The people list's priority (A, B, C) and lane, and the job-posting class, are model outputs that code only checks for allowed values and a verbatim sentence. Ask answers are the model's own wording; only the [R#] row citations are checked, not the meaning. If the judge model and the extraction model ever resolved to the same profile, every claim needing a judge would be silently capped to Probable with no error.

12 Uploaded files

Customers can upload spreadsheets, PDFs, call transcripts, a zip or a whole folder. Every file is treated as hostile until proven otherwise.

  • Upload goes straight to storage through a resumable session; the API never sees the bytes. The file lands in a quarantine area.
  • The type is detected from the bytes, not the name. Audio is rejected. The virus scanner (ClamAV sidecar) must answer; if it errors the file is rejected and stays quarantined (fail closed).
  • Each part is parsed in its own locked-down child process: empty environment, resource limits, an audit hook refusing network, process and writes, and a time limit. This is a speed bump, not a true security boundary.
  • Personal data is redacted, text is cut into 400-800 token passages (prose) or one row per row (spreadsheets), and spreadsheets become queryable tables.
  • A file with no account stops until the user confirms the company; the system never guesses.
  • File-mode research (POST /v1/runs, input_mode=file) is a separate 7-node graph that researches only the uploads and produces the Internal Only document; an optional follow-up creates a separate public-research run with its own approval.

14 Schedules, credits and money

There is no payment processor in the code. "Billing" is an internal credit ledger.

Scheduled refresh (live)

Each account can refresh every 3 days, weekly, every 2 weeks or monthly. Cloud Scheduler calls /tasks/schedules-tick every 15 minutes; for each due account the system estimates the cost, checks the owner's monthly limits, reserves credits and queues a normal research job (scoped to jobs, people, topic or full). There is no bound on how many due accounts one tick starts; with caps off a large batch could all start together.

Credits

  • 1 credit = $0.05. Estimates per scope (config/credits.yaml): jobs 20, people 60, topic 40, full 250. The file itself says the numbers are placeholders.
  • Credits are reserved when research starts, settled once when it ends at min(ceil(real spend / $0.05), reserved), and released on failure. With caps off the platform absorbs any spend above the reservation.
  • The ledger (credit_entries) is append-only. A nightly Cloud Run job spend-invariants checks it.
  • config/billing.yaml describes settlement "proportional to budget used" but the code does something else; treat that file as notes.

Built but not connected

The monitoring product (cheap probes, signal scoring, alert rules, weekly digest) exists in src/refresh, src/signals and src/alerts and is tested, but nothing calls it: run_probe is imported only by tests. The retention and alert-digest scheduler entries are paused and point at routes that do not exist. The alerts a user sees today are in-app notifications such as "research finished", sent by a 5-minute relay. CRM write-back is also dormant.

How the browser reaches the API

  • The browser talks only to its own origin. /v1/ goes through a streaming proxy** (app/v1/[[...path]]/route.ts). The comments call it a rewrite, but next.config.ts has no rewrites.

Uploads go straight to object storage, not through it.
  • proxy.ts sets a per-request CSP nonce (no inline scripts or styles) and does no authentication. The (client)/layout.tsx is the real login check: it reads /v1/me and redirects to /login on 401.

  • Live data: EventSource for the Research board and run progress, a streaming fetch for Ask answers, polling fallbacks, and router.refresh() on some pages. There is no Redux or SWR: server components fetch; client components use plain state.

Sign-in, sessions and CSRF

  • Customers sign in with company SSO (OpenID Connect or SAML) or a first-party password (Argon2id; invite-only, no self-signup). The session is a 256-bit random token in an __Host-ai_session cookie (HttpOnly, Secure, SameSite=Lax); the database stores only its SHA-256. Idle timeout 30 minutes, absolute 8 hours.
  • CSRF: every unsafe request must carry X-CSRF-Token, an HMAC of the session id under a server key in Secret Manager.
  • MFA: 27 routes demand a fresh MFA step-up. Local password login is refused for admins because no TOTP verifier is wired, so admins can only enter through SSO with MFA.
  • Staff use a Google ID token, email allow-lists and MFA on every call, even reads. To touch a tenant's data a staff member also needs a time-boxed support grant that a customer admin created; every call is audited in both places.
  • Worker tasks require a Google-signed OIDC token for the worker audience from one named service account, and carry ids only.

Other conventions

  • Errors are application/problem+json. Messages other than invalid token, forbidden and not found are replaced by the status title, so internals never leak.
  • Rate limits stack: Cloud Armor at the edge (300 s ban), sign-in buckets in Redis, per-user money and compute buckets (config/rate_limits.yaml, all marked "proposal, unmeasured"), monthly per-user counts, per-thread chat limits.
  • Idempotency: Idempotency-Key on POST /v1/runs; request_id in the body on research, refresh, ask and download-everything.
  • The server has exactly one HTTP middleware (request id, logging, metrics, security headers). No CORS layer exists, because the browser only talks to its own origin.
  • API documentation pages (/docs, /redoc) are disabled in staging and production.

How customers are kept apart

  1. Every tenant table has a non-null tenant_id and FORCE ROW LEVEL SECURITY, which applies even to the table owner. The policy compares tenant_id with app_tenant(), a function reading a setting that only exists inside the current transaction.
  2. The application connects as role app_rw, which owns nothing and cannot bypass the policies. If no tenant is set, every policy matches zero rows (fail closed).
  3. tenant_txn(tenant) is the only normal way to run a query; it sets app.tenant_id, app.user_id and app.scope for that transaction only.
  4. A second layer (migration 0063) makes 102 tables private to the user who owns them, so even inside one customer a user cannot see another user's accounts, files or chats unless the scope is system.
  5. Work that must cross customers (sweeper, schedule tick, sign-in lookups, concurrency governor, purge) goes through named SECURITY DEFINER functions that return ids only, owned by no-login roles. Each carries a "reviewed:" comment enforced by a lint.
  6. Ledgers are insert-only (no UPDATE or DELETE grant). Child tables use composite foreign keys (tenant_id, parent_id) so a row can never point at another customer's parent.
  7. Proof: 12 isolation test files, a nightly isolation-check that probes every tenant table and read route, and an audit hash chain verified nightly.
Where isolation could still fail

The whole model rests on code always going through tenant_txn. Raw sessions and untenanted_session() exist for jobs, and system scope is a context variable any code can set. Foreign keys bypass row-level security. The purge roles (migrations 0096-0097) are recent and lightly exercised. All services share one broad app_rw role.

26 Taking over safely: a first-week guide

Practical steps, ordered so nothing costs money or breaks anything before you understand it.

Do not do these

Costly or destructive
  • Do not start a live research run (the live compose file or a deployed staging account) to "try it". A run reads hundreds of pages and calls the paid AI; earlier failed runs cost about $500.
  • Do not run tests with -m eval or -m live. They call the real paid model. Always use -m "not eval and not live".
  • Do not run two test sessions against the same scratch database: the test fixture drops and recreates it.
  • Do not source .env before testing; its DATABASE_URL hijacks the test database.
  • Do not apply an old Terraform plan. Always make a new plan first.
  • Do not run unwanted-things/cleanup.sh until you have read it; it holds the irreversible steps.

5. Research prompts in detail

All agent prompts (#1-#6) are Markdown files, 6-21 lines, every instruction line ends with a trace tag like [S5] (skill step) or [platform rule 3]. They are loaded by agents/runtime.py::load_prompt with a sha256 hash. Each call is wrapped (section 6) and carries the output JSON Schema (output.model_json_schema()) as a trailing "Answer with one JSON object, no prose and no code fence, that validates against this JSON Schema: ..." and as Claude structured output. Output validation common to all six: pydantic with extra="forbid" (agents/schemas.py::_Strict), then runtime.call_agent checks (G4 schema, G9 client text scrub + injection echo, G13 token budget).

Common guard in call_agent (agents/runtime.py:96-137): 1. code-only agents (no task kind) refused (G5); wrong input schema refused (G13); 2. meter.charge_call() and reserve_tokens(estimate) before the call: a call whose estimated size would exceed the agent's token budget is refused before it is paid for; 3. schema failure -> OutputRejected(G4, schema_invalid): nothing from the output is kept; 4. client_bound=True (distill only): sanitize_client_value scrubs tool names and rejects provider/person names (G9); 5. any string in the output that contains a canary or instruction marker (config/grading_policy.yaml: CANARY-7f3a9e, <<SYSTEM>>, "ignore previous instructions", "system prompt", "you are now", ...) -> injection_echo rejection.

10. "The AI never chooses a grade": how code enforces it

Grades: engine A/B/C/D/CONFLICTING/BLOCKED, product Confirmed/Probable/Hypothesis/Lead/Internal Only. Layers:

  1. No place to write one. Every model output schema is extra="forbid": FactCandidate, PersonCandidate, Claim, ExtractionOutput, DistillOutput, SenseCheckOutput (agents/schemas.py), and the grading ProposedSourced/Synthesis/Absence (grading/schema.py: "has no grade, confidence, tier, lineage or read flag; extra='forbid' rejects any attempt (G1)"). A grade/tool_call/tenant_id in a reply is a schema failure and the whole output is rejected (test test_output_schemas_have_no_grade_or_tool_fields).
  2. Grade = pure code. grading/engine.py (no I/O, no model): evidence weight by source tier x recency half-life (config/grading.yaml), strongest per lineage group, quantised confidence compared to thresholds -> engine grade. grading/product.py::product_grade is one pure function with a configured precedence (config/grading_policy.yaml product_precedence.order: no_evidence, conflicting, internal_only, primary_read, unread_match, aggregator_only, engine_a_or_b, engine_c_or_synthesis, engine_d_or_secondary_only).
  3. "Confirmed" cannot be claimed by the model. It requires read_in_primary_this_run computed by grading/primary.py from the ledger (how the text was obtained: origin_by_operation: only scrape_job_page is full_page_read; read_page is cached_copy; web_search is search_snippet), not from anything the model said. A model-declared origin is only ever lowered (extraction._origin).
  4. Evidence is code-verified. The quote must be verbatim (after NFKC) in the stored text of a source of THIS run at that URL (grading/spans.py::verify_span, verify_url, value_support) and G4 in agents/guards.py::evidence_problem checks it earlier. Fabricated quotes/URLs/titles/names/tenures are dropped and counted.
  5. Guard G2 fail-closed: if the engine ever promoted an unread keyword match or date range above Lead, lead_check raises unread_match_promoted and the run ends partial (this happened once; guide 2.6).
  6. Models can only lower. Judge: unsupported drops the claim; unavailable caps it (C / Probable / unjudged) - apply_support_verdict. Verifier (V1 only): verify/policy.py "downgrade only", property-tested never to raise. Sense-check contradictions: mark_conflicting supersedes with the Conflicting cap, "never raises a grade".
  7. Single write path. Facts are written only by grading/repo.py::record_graded_fact (append-only; supersede for changes). The ABM EngineGrading port: "Nothing here assigns a grade."
  8. Statements to a client: statement_policy - only Confirmed may be stated; distill's statable_fact_ids and states_unstatable() force other facts into questions; restates_grade() drops claims that name a grade; Summary/Word rendering shows the engine's grade.
  9. Counts are code: job platform counts come from stored rows (jobs/counts.py), Ask platform-tier counts from count_tiers, Ask query counts from query_table.row_count; the model reports them.
  10. Not covered by this rule (be aware): the people list priority A/B/C and lane are model outputs (validated only for allowed values/quotes); the job posting class is a model output but needs a verbatim sentence and, for Build/Admin-owner, a second model's agreement; Ask prose is the model's wording (citations checked, not meaning).

A.3 Failure modes and what the code does
  • Queue unreachable at start/slice-0/timeout: logged, state committed, sweeper recovers within ~15 min (recovery.py). Cloud Tasks keeps a finished task's name for about an hour (guide 02 s2.7), so a repeat of a hand-off whose first task already ran can land late - late, not lost.
  • Worker killed mid-slice: retries at ~+10/+30/+70 s answer 503 busy; the +150 s retry finds the lease's heartbeat >90 s old, takes it (new epoch) and resumes from the last node checkpoint (checkpoints are per graph node, not per call: a killed interpret re-runs the whole node, with finished model replies/provider calls replayed from model_reply_log/tool_calls).
  • Worker alive but event loop blocked (the 2026-10-28 YAML-parse freeze): Cloud Run's liveness probe kills the instance; obs/stalldump.py writes the main-thread stack. Not fully proven fixed (06 #5).
  • Hung provider call: per-row 540 s ceiling in pull, 300 s per single call (SINGLE_CALL_CEILING_S, connectors/base.py:70), per-slice timer 1650 s, 3-empty-slice cut-off.
  • Duplicate/stale deliveries: all handled by named tasks + begin_slice expected-counter + lease.
  • max_slices: see D1 (non-existent on staging).
  • Money: credits are charged from real spend, never above the reservation. With caps off the platform silently absorbs any spend beyond the reservation (min(used, reserved) at credits.py:408).
