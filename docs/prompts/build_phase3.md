## 3. Anti-hallucination protocol (run time)

Each rule has a "lying scenario" test (section 7). Prefixes: **TN** tenancy and isolation, **ID** identity, **AU** audit, **VW** views and exports, **CN** connectors, **MT** metering, **AD** admin and support, **PL** pilot.

| # | Rule |
| --- | --- |
| TN1 | **Isolation is generated, not hand-written.** A catalog-driven matrix enumerates every tenant table, view, route, storage path, cache key, job and event type and attempts, as tenant B, every read, write, update, delete, list, search and download of tenant A's planted canary rows, files and vectors; it fails if anything is **not covered by the matrix** (a new table or route without an entry breaks the build). It runs on every build and release. |
| TN2 | **Deny by default.** Every route is in the API policy table with roles and a tenant-source rule; a route absent from it returns 403 and fails a test; tenant id is taken only from the verified session, never from body, path, query, header or model output (including `{domain}` and view ids, which are resolved **inside** `tenant_txn`). |
| TN3 | **Database layers hold if the app is wrong.** Forced RLS with `USING` and `WITH CHECK`, `TO app_rw`, `security_invoker` views, no BYPASSRLS, the catalog check returns no rows; a test runs the app with the authorisation layer disabled and the database still refuses cross-tenant access. |
| TN4 | **Per-tenant storage.** Paths are built by one function from the context tenant (`tenants/<tenant>/...`); listings are prefix-scoped; signed URLs are short-lived, bound to tenant, object and content hash, and refuse another tenant's object; cache and queue keys carry the tenant prefix; branding and uploads live under the tenant prefix with the tenant's key tier. |
| TN5 | **Settings are versioned tenant objects.** Platform lanes, people scope, exclusions, the pursuing client and branding are insert-only versions; a run records the settings version it used; **exclusions are enforced in code at pull time and again at render time** (an excluded company or person never reaches a table or export). |

| ID2 | **Membership is checked on every request** (cache about 60 s, source): a removed or suspended user loses access within that bound; role changes take effect within it; an IdP login for an unknown user is rejected or provisioned **only** if the tenant enabled just-in-time provisioning for a verified domain (D-62). |

| AU2 | **The audit is insert-only, chained and exportable.** Per-tenant hash chain verified by a job; no UPDATE or DELETE grants; tenant admins export it (CSV, scanned by `scan_client_output.py`: categories, no provider names, credits or cost); actors, resources, times, request ids and outcomes only, never content. |

## 7. Test harness (build before the code)
Location `tests/phase3/`, `tests/isolation/`, `web/tests/`, real Postgres, virtual `Clock`, fakes from `tests/fakes/`, fixtures labelled `synthetic`, three tenants with planted canaries.
1. **Generated isolation matrix (TN1):** every table, view, route, storage path, cache key and event type against cross-tenant read, write, update, delete, list, search, download and signed-URL reuse; failures on any uncovered object; a deliberately broken policy in a scratch database **must be caught**; the same matrix runs with the authorisation layer disabled (TN3); `check_rls_catalog.sql` and the lint in CI.
2. **Route catalog tests:** every route has a policy and an audit class; absent means 403; tenant ids in body, path, query and headers are ignored or rejected; `{domain}` and view ids resolve only inside the tenant.
3. **Identity:** OIDC and SAML positive flows and the negative suite (wrong issuer, audience, expired, replayed assertion, missing `InResponseTo`, signature wrapping, unsigned, altered tenant claim, unknown user, disabled JIT, unverified domain, state and PKCE mismatch, open redirect); membership removal and role change within the cache bound; session fixation, CSRF, idle and absolute timeout, revoke-all, step-up; the full role-by-action table against D-61 including "last admin" and "self-promotion".
