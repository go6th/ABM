# 05 · Questions a CTO, a security reviewer or a buyer will ask

Answers come from the evidence in `01`–`03`. "Today" is the working tree of `feat/final-product` and the live project on 2026-11-10. "After" is the state once the roadmap in `04` is done; it is omitted where nothing changes. Finding ids point to `03-findings.md`.

## Tenancy and access

**1. How are tenants isolated from each other?**
Today: every table with tenant data (186 of 222) has row-level security enabled and forced, keyed on a per-transaction tenant setting; the application connects as roles that cannot bypass it (V `migrations/0002_rls.sql`, `0101_service_roles.sql`). Every storage object key starts with the tenant id and downloads are checked against the session's tenant (V `src/tenancy/storage.py:183-220`). Cache keys and the vector index are tenant-scoped (V). We found no cross-tenant read path.
After: unchanged design, plus a nightly isolation check that actually runs and alerts a person (SD-03).

**2. Could a bug in one API route leak another customer's data?**
Today: the database refuses rows from other tenants even if a query forgets a filter, because RLS is forced and the tenant is set per transaction. A bug could still expose another *user's* private rows inside the same tenant, since "system scope" is an application-level switch (I, `0063_private_workspaces.sql:96-99`).

**3. Can your staff see our data?**
Today: staff read tenant data through support grants that a tenant admin creates for one named person, for at most 2 hours (read) or 30 minutes (write), with every call audited and visible to the tenant (V `src/admin/support.py:51-85`). There is one bypass: an operator can create an invite and receive the link (SD-11). Some staff console views show tenant metadata without a grant (V `admin_console.py:1-35`).
After: invites go only to the invitee and staff-created members need a grant.

**4. How do your staff sign in, and is MFA enforced?**
Today: Google sign-in with an allow-list. Two-step verification is assumed for Google, not checked, and one staff operator is a personal Gmail account that is also a cloud project Owner (SD-13).
After: Workspace accounts only, 2SV enforced by Workspace policy, group-based least-privilege IAM.

**5. Do you support our SSO? What stops someone else from claiming our domain?**
Today: yes, OIDC and SAML per tenant with modern protections (state, nonce, PKCE; signed SAML; replay protection) (V `src/identity/`). Nothing stops another tenant from listing your domain for sign-in discovery (SD-10).
After: domains need a DNS TXT proof and can be claimed by one connection only.

**6. Is there an audit log, and can it be trusted?**
Today: yes, per tenant, hash-chained, insert-only for the app, with read events recorded before data is returned (V `src/audit/`, `api/guard.py:144-165`). The chain uses no secret, the off-site archive is unused, and the nightly check stops at 50,000 rows (SD-12).
After: incremental checks and a daily signed head stored in a retention-locked bucket.

## Money

**7. Can a customer be charged twice for the same research?**
Today: no. Reservations are serialised per tenant with a row lock, a repeated request id returns the first job, one open job per account, and settlement is idempotent under redelivery (V `replica/credits.py:245-408`; unique keys in `migrations/0053_replica.sql:131`, `0063_private_workspaces.sql:1729`).

**8. Can a customer be charged for work that failed?**
Today: failed runs are refunded in full; runs that end PARTIAL are charged their spend up to the reservation (V `runs/lifecycle.py:~955`; `credits.py:408`). Some PARTIAL endings are caused by the platform (a slice waiting too long in the queue), so a customer can pay for a run the platform cut short (SD-08).
After: hand-off fixes remove those platform-caused endings.

**9. Can a single run cost you more than the customer pays?**
Today: yes. Caps are off on the live services; a run may spend without a dollar limit, and the customer is charged at most the reservation (250 credits, $12.50, for a new research) (SD-02).
After: a hard ceiling per run and per Ask thread, caps on, provider-side limits and an hourly spend alert.

**10. How do customers pay?**
Today: they don't through the product. Credits are a monthly pool set by staff, not enforced for new research, with no invoicing (SD-20).
After: pool enforced and monthly invoices generated from the credit ledger.

**11. If we leave, is our billing history kept?**
Today: the tenant deletion plan would delete it by cascade (SD-01).
After: the ledger is protected by a restricting foreign key and an FK-aware plan check.

## Data and privacy

**12. Where is our data stored?**
Today: Google Cloud, region us-central1, in Cloud SQL (private IP, encrypted with a customer-managed key) and Cloud Storage buckets with uniform access, public access prevention and the same key (V `gcloud sql instances list`, `gcloud storage buckets list`). Redis (memory only) holds rate-limit counters and a 7-day cache index that includes provider answers (V).

**13. Where does our data go outside your cloud?**
Today: to data providers (search queries, company names, page URLs) and to model providers (scraped text, extracted facts, people data and, in Ask, whole uploaded files and table rows): Anthropic, and Ollama Cloud when Kimi is chosen. The data-class guard is off and retention terms are unverified; the published sub-processor list names neither (SD-05).
After: zero-retention terms or Vertex AI in-region for tenant data; per-tenant guard; complete sub-processor list.

**14. You store data about named people. Can one of them ask you to delete it?**
Today: no working process. Person erasure code exists but is not exposed; there is no request-handling flow (SD-04).
After: a person erasure job usable by tenant admins and staff, covering the database, objects and cache, with an audit record.

**15. How long do you keep data?**
Today: raw provider payloads 30 days, quarantined uploads 1 day; everything else indefinitely, including model outputs and run checkpoints. Written retention windows are not enforced (SD-04, SD-29).
After: a scheduled retention job per data class.

**16. When we delete an account or leave, what is actually removed?**
Today: deleting an account erases its database rows in one transaction and then deletes objects in the background; a failure there is only logged (SD-31). Deleted objects stay recoverable for 7–14 days (versioning, soft delete) and in database backups for 7 days. Tenant offboarding is a proposal that keeps people data and model outputs and misses one object prefix (SD-04).
After: erase via retried tasks, complete prefix list, and stated recovery windows.

**17. Can a malicious uploaded file hurt you or other customers?**
Today: uploads go to a quarantine bucket, are type-checked by content, refused if they contain macros or executables, scanned by ClamAV (refused if the scanner is down), and parsed in a sandboxed child process without network access (V `src/documents/scan.py`, `sandbox_child.py`). LibreOffice checks run outside that sandbox (SD-38).

**18. Could text inside a web page or file trick the AI into leaking data?**
Today: Ask's tools only read the caller's own tenant data; there are no write tools. The remaining channel is the web-search tool: the model writes the queries and they go to the search provider unmetered (SD-15).
After: web tools go through the same controlled pipeline as research calls, with query limits and a per-tenant switch.

## Reliability

**19. What happens if a worker dies in the middle of a research run?**
Today: Cloud Tasks retries the slice; after about 150 s the retry takes over the stale lease and resumes from the last checkpoint, so only the step in progress is repeated and paid calls are not paid twice (V `runner.py:206-219`; `ledger.py:233-323`). If all retries fail, the sweeper ends the run as PARTIAL about 40 minutes later (V `runs/sweeper.py:120-163`).
After: same, with a 30 s graceful stop and one slice per instance so a single crash affects one run.

**20. What happens if the database goes down?**
Today: the whole product is down until the zone recovers or a restore completes. Nobody is alerted (SD-03, SD-06).
After: automatic failover to a standby in another zone in about a minute; a person is paged.

**21. What happens if Redis goes down?**
Today: all paid provider calls fail, so research stalls; uploads, exports and downloads return 503 (SD-07).
After: Redis has a replica; if it still fails, the limiter falls back to local limits and research continues.

**22. What is your recovery point and recovery time?**
Today (I): within the region, point-in-time recovery gives minutes of data loss; losing the region means restoring from backups that live in the same region, with recovery time in hours and no drill on record.
After: cross-region backups, a quarterly restore drill with measured numbers.

**23. Do you run in more than one region?**
Today: no; everything is in us-central1.
After: still single-region active, with a documented cold-standby restore in a second region. Active-active is not recommended at this stage.

**24. How do you know when something is broken?**
Today: you don't, unless someone looks. 17 alert rules exist and send to nobody; there is no error tracker (SD-03).
After: alerts to email and Slack with a named on-call person, plus Error Reporting.

**25. Can you follow one user request from the browser to the worker?**
Today: through api logs yes (request id); into the worker only by run id, because the request id is not passed through Cloud Tasks (SD-27).
After: request id and trace context travel with every task.

## Security and operations

**26. Are any endpoints open to the internet without authentication?**
Today: only the sign-in routes, health probes on the web, and static assets. The api and worker cannot be reached from the internet at all (internal ingress plus IAM) (V). Background-task routes check a Google-signed token in code as well.

**27. Are secrets in your code?**
Today: no. Real keys live in Secret Manager with per-secret access; CI runs gitleaks; tracked files contain only synthetic test values (V). Rotation is manual.

**28. How is code deployed, and could untested code reach production?**
Today: yes, it could. Releases are built from a laptop, including uncommitted patches, without running tests or scans (SD-09).
After: releases only from CI on a protected branch, with tests, image scanning and a drift check.

**29. Is your infrastructure defined as code?**
Today: yes, Terraform covers the whole stack, but services were last changed by `gcloud` and drift is unmeasured (SD-09). The `prod` environment has never been applied (SD-17).
After: weekly drift plan; production project built from the same code.

**30. Do you have separate production and test environments?**
Today: no (SD-17).
After: yes.

**31. How do you protect against DDoS and common web attacks?**
Today: Google's global load balancer with Cloud Armor: OWASP rule sets, per-IP rate bans (stricter on sign-in) and Adaptive Protection (V `gcloud compute security-policies list`).

**32. What browser-side protections do you use?**
Today: a strict per-request nonce Content Security Policy, HSTS, frame denial, no-referrer, same-site and host-prefixed session cookies, CSRF tokens, and a same-origin check on every write (V `web/proxy.ts`, `web/next.config.ts`, `src/identity/csrf.py`).

## Scale and cost

**33. How many research runs can you handle at once?**
Today: six slices run concurrently; a seventh run waits in the queue, and a long wait can end it early (SD-08, SD-16).
After: worker scaled to 10+ instances with one slice each and the queue matched to that.

**34. What breaks first as tenants grow?**
Today (I): the run queue and worker size, then platform-wide provider call ceilings (4 per provider, 8 for search, shared by every tenant), then the 1-vCPU database. Scheduled ticks loop over tenants one by one and will overrun their deadlines with tens of tenants (SD-16).

**35. Can one customer slow down the others?**
Today: partly protected. A tenant can use at most half of each provider's platform-wide call slots (V `config/parallel.yaml:96-125`). There is no per-tenant limit on concurrent runs, and the database is shared on 1 vCPU (SD-16, SD-19).
After: per-tenant run concurrency from the plan, statement timeouts, larger database.

**36. Which AI models do you use and can their behaviour change under you?**
Today: Claude models through the Anthropic API by default, Kimi K3 through Ollama Cloud when chosen; Grok is listed but not configured. Model ids are aliases, so a provider can change the model behind a name; the returned model id is recorded per call (SD-36).
After: pinned snapshots where available.

**37. Do you train models on our data?**
Today: no training code exists in the repository (NF: no fine-tuning or training calls in `src/`). Whether the model providers keep or use the data depends on their terms, which have not been verified (SD-05).

**38. How much technical debt is there?**
Today: two run engines (one deprecated but reachable), several packages written but not wired in (refresh engine, signal intake, alert engine), and dead API modules. They add test and review cost but do not run in production (SD-28).
After: one engine; unwired code moved out of the product source.
