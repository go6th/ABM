Backend, as the client app uses it

Every client page was traced to its API calls and handlers. Two drift checks pass ("openapi snapshot OK", "generated client OK"), so no page calls a missing endpoint. The problems are slowness, internal codes in responses, and status words the screens have to translate.

Slow because of how pages load

  • Every page change costs 4 calls (me, chat threads, notifications, model choices). GET /v1/me also writes a "last active" row and runs about 7 queries. The chat list returns 100 threads to show 6.
  • Opening an account can rebuild files inside a read. GET …/workspace may regenerate stale tables (account_workspace.py:155-176) and runs a count with about 20 subqueries. When it passes the web's 10 s limit the user sees "This account could not be loaded".
  • Each data table page re-downloads the whole bundle from storage and slices it in memory (parity/service.py:344). A tab with K tables costs K+1 downloads.
  • A running research is polled in three ways at once: run status every 5 s, live spend every 5 s (by accident: RunSteps.tsx:278), and a 1 s database poll per open tab.
  • The Research board stream rebuilds the whole snapshot every second per viewer, and reconnects every 5 s forever when nothing runs.
  • The document page makes up to 50 calls in a row before it shows anything.
  • Accounts list computes every account, then limits; the web asks for 200 and never pages, so account 201 onwards silently disappears.

Internal codes sent to the client

  • GET /v1/runs/{id} returns the raw stop reason (can be a Python error name), stop detail ("made no progress in N slices"), gate defect codes and paid/cached call counts. The run page prints them. A good translator already exists (replica/workspace.stop_text) but this endpoint does not use it.
  • Research board shows "Reason: credit_cap_reached"; a running job is labelled "Starting".
  • Error texts mention "tenant"; Delete account shows "(403 csrf_refused)".
  • Teammates: "already a member" can never show, because the API turns that reason into "Conflict" (api/problem.py:30).

Ten status vocabularies

Run (10 uppercase values), research job (6 lowercase), account state (7), document (12 + 8 stages), coverage (6), step (6), live spend, download, gate ("pass" and "passed"), and error type (slug or number). Proposal: one research object everywhere with state waiting, running, needs_you, done, done_with_gaps, stopped, cancelled, a server-written label and one human sentence, never a code.

Backend: safety and the changes to make

What holds

  • Default-deny routes; role, membership and CSRF checks on every write; row-level security per workspace.
  • Cross-site writes refused at the web proxy.
  • Confirm-twice (428) is enforced on all four start doors: new research, resume, new run, refresh. Automatic starts stay off.

Gaps

  • Continuing a paused run skips confirm-twice, including past the 3x token guard, and "Auto continue" approves later pauses with no click.
  • POST /v1/runs with a company domain skips the per-user research quota that POST /v1/research applies.
  • No short-term rate limit on new research, refresh or Ask (only monthly quotas).
  • About 60 endpoints with no client screen are reachable by any client session and ship 154 KB of contract code to every browser.
  • Strict response parsing: a new API field breaks older web pages until both are redeployed.
