Summary

The app works, but it shows clients too much of how it works. The account page carries 50+ controls, research can be started from six places, and internal words from the pipeline reach client screens. The fix is mostly removal: fewer pages, one main action per screen, plain words, and a flatter look in the white and pastel palette you already chose.

Client web audit and redesign2

What is wrong today

Six problems repeat across the client app. Each one is backed by what we saw on screen and in the code.

Internal words reach clients

Run steps called "Summary homework", "Distill" and "Pre delivery gate"; "checklist rows reported"; "Units used"; "withheld"; "Lanes"; "passages", "Indexing", "Raw pull"; "Stay local"; HTTP status codes in the Delete account error; QA banners that say a view is "not to be quoted".

The account page is overloaded

About 2,600 lines of code and 50+ controls. A 17-link Deep dive rail, 4 tiles that repeat 4 of those links, a progress card, summary, findings, a composer that leaves the page, a full delivered-files viewer and two file cards. Five download buttons, two of them both called "Download all" doing different things.

The same job in many places

Start research: Add account, New research, the Research board, Refresh, Resume and Ask's search toggle. Watch a run: the account card, the Research board and the run page. Uploaded files: four different views. Schedule: a page, a button and a column.

Bugs visible on screen

File analysis says "Your files speak to undefined" and "Analysis of 0 files" while the account lists 19 ready files; finding text overlaps the file path. The run page says every step is Done next to "0 of 6 rows reported" and 0 tokens. Jobs show raw values like "data_ai". People filters all read 0.

Two design systems

Two page frames, four table components, five badge styles, three input styles, six browser confirm boxes plus a custom modal, 21 font sizes, a second off-palette colour set for the token card, and the logo still in the old colours.

Not ready for outside eyes

Privacy and Terms are live with "[Effective date]" and "[Company legal name]". Google and Microsoft will read the privacy page when they review the Mail and drive apps. The sign-in workspace picker shows raw IDs.

The run page shows the pipeline, not the result

This page is reachable by every client. It lists 13 internal steps, all marked Done, beside "0 of 6 checklist rows reported". The token card says 0 tokens and $0.00 for a finished run. Below it, a 33-row table says "Not yet reported" and "No proof recorded" on almost every line, under a green "Completed".

A client reading this cannot tell whether the research worked. The proposal replaces it with five plain steps, live counts of what was found, and one sentence on what could not be found and why. The pre-delivery gate, defect codes and the coverage table stay on the operator console.

Also on this page

  • "Units used so far" with a Refresh button in the middle of the page
  • A different page frame from every other screen (.page vs .pg)
  • Client-only render, so it is blank until all calls return

Rules

  • Two corner sizes: 8px for controls, 12px for panels. No drop shadows.
  • One main (blue) button per screen. Delete lives in a … menu, never beside the main action.

  • Plain words only: what the user will see, not how the system works.
  • No inline styles in the app (your CSP), so all of this lives in tokens and classes.

Backend, as the client app uses it

Every client page was traced to its API calls and handlers. Two drift checks pass ("openapi snapshot OK", "generated client OK"), so no page calls a missing endpoint. The problems are slowness, internal codes in responses, and status words the screens have to translate.

Slow because of how pages load

  • Every page change costs 4 calls (me, chat threads, notifications, model choices). GET /v1/me also writes a "last active" row and runs about 7 queries. The chat list returns 100 threads to show 6.
  • Opening an account can rebuild files inside a read. GET …/workspace may regenerate stale tables (account_workspace.py:155-176) and runs a count with about 20 subqueries. When it passes the web's 10 s limit the user sees "This account could not be loaded".
  • Each data table page re-downloads the whole bundle from storage and slices it in memory (parity/service.py:344). A tab with K tables costs K+1 downloads.
  • A running research is polled in three ways at once: run status every 5 s, live spend every 5 s (by accident: RunSteps.tsx:278), and a 1 s database poll per open tab.
  • The Research board stream rebuilds the whole snapshot every second per viewer, and reconnects every 5 s forever when nothing runs.
  • The document page makes up to 50 calls in a row before it shows anything.
  • Accounts list computes every account, then limits; the web asks for 200 and never pages, so account 201 onwards silently disappears.

Internal codes sent to the client

  • GET /v1/runs/{id} returns the raw stop reason (can be a Python error name), stop detail ("made no progress in N slices"), gate defect codes and paid/cached call counts. The run page prints them. A good translator already exists (replica/workspace.stop_text) but this endpoint does not use it.
  • Research board shows "Reason: credit_cap_reached"; a running job is labelled "Starting".
  • Error texts mention "tenant"; Delete account shows "(403 csrf_refused)".
  • Teammates: "already a member" can never show, because the API turns that reason into "Conflict" (api/problem.py:30).

Ten status vocabularies

Run (10 uppercase values), research job (6 lowercase), account state (7), document (12 + 8 stages), coverage (6), step (6), live spend, download, gate ("pass" and "passed"), and error type (slug or number). Proposal: one research object everywhere with state waiting, running, needs_you, done, done_with_gaps, stopped, cancelled, a server-written label and one human sentence, never a code.

Client web audit and redesign22

Backend: safety and the changes to make

What holds

  • Default-deny routes; role, membership and CSRF checks on every write; row-level security per workspace.
  • Cross-site writes refused at the web proxy.
  • Confirm-twice (428) is enforced on all four start doors: new research, resume, new run, refresh. Automatic starts stay off.

Gaps

  • Continuing a paused run skips confirm-twice, including past the 3x token guard, and "Auto continue" approves later pauses with no click.
  • POST /v1/runs with a company domain skips the per-user research quota that POST /v1/research applies.
  • No short-term rate limit on new research, refresh or Ask (only monthly quotas).
  • About 60 endpoints with no client screen are reachable by any client session and ship 154 KB of contract code to every browser.
  • Strict response parsing: a new API field breaks older web pages until both are redeployed.
